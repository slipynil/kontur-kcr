# Import API и Import Worker

Из этого каталога запустите `docker compose up --build -d`. Compose поднимает Import DB и RabbitMQ, выполняет миграции и запускает два процесса.

| Процесс | Точка входа |
|---|---|
| Import API | `uvicorn import_worker.api:create_app --factory --host 0.0.0.0` |
| Import Worker | `python -m import_worker.consumer` |

API доступен на `http://import-api:8000` внутри сети Compose. Gateway проверяет права администратора и передаёт `X-User-Id` при загрузке. Для запуска вне Compose установите Python 3.14 и Poetry 2.5.1, выберите интерпретатор командой `poetry env use 3.14` и выполните `poetry sync`. Установите `IMPORT_DATABASE_URL`, `IMPORT_AMQP_URL` и `IMPORT_UPLOAD_DIR`, примените `poetry run alembic upgrade head` и запустите обе команды через `poetry run`. Для стенда нужны свои учётные данные PostgreSQL и RabbitMQ.

Для изолированной разработки задайте `IMPORT_LOCAL_CLIENTS_URL` и `IMPORT_OPERATOR_WORK_URL` как базовые URL сервисов, доступные из сети Worker. Реестр завершается после подтверждения Clients, срез — после подтверждения всех частей в Operator Work. Если все наблюдения среза уже были приняты, повтор завершается как `COMPLETED` без изменений. Отклонённый целиком пакет получает `FAILED`. В отчёте номер строки 0 обозначает сообщение о книге или листе.

При обновлении до `0004_snapshot_metadata` остановите приём новых загрузок и завершите пакеты реестра старым Worker. После этого остановите старые процессы Import API и Worker, примените миграции Clients DB и Import DB и запустите обновлённые сервисы. При незавершённом применении реестра в Clients миграция Import DB прервётся, сохранив исходные значения для повтора запроса. Подробнее в [ADR-0016](../../docs/adr/0016-snapshot-only-import-metadata.md).

Исходный квартал для `SNAPSHOT` задаётся столбцом `Исходный квартал` или `quarter` в формате `YYYY_QN`. В исторических листах без этого столбца используется выбранный квартал. Для выгрузки с остатками нескольких исходных периодов указывайте период каждой строки. Пустое значение в этом столбце и исходный квартал позже выбранного считаются ошибками. Правило для годового листа описано в [ADR-0013](../../docs/adr/0013-standalone-annual-snapshot.md). Составные листы и листы с явно другим кварталом пропускаются.

Срез должен содержать заголовки кода КЦР и двух счётчиков, например «Документов всего» и «Всего не отправлено документов». Поддерживаются распознаваемые варианты заголовков и произвольный порядок столбцов. В обезличенном срезе без отдельной колонки «Код КЦР» распознанный заголовок обезличенного идентификатора используется как код. Размер загружаемого файла по умолчанию ограничен 32 МиБ через `IMPORT_MAX_UPLOAD_BYTES`.

Ошибки доступны в JSON-отчёте и отдельной книге по внутреннему маршруту `GET /internal/v1/imports/{batch_id}/errors.xlsx`. Книга содержит лист, физический номер строки, код КЦР и причину. Публичный маршрут для скачивания требует подключения в Gateway.

В RabbitMQ передаётся JSON с `batch_id`. В случае сбоя публикация повторяется по журналу Import DB, а запрос к Clients повторяется с сохранённым содержимым и тем же UUID. Worker подтверждает успешно доставленные части по отдельности и продолжает с первой неподтверждённой. При окончательном HTTP-отказе Operator Work статус части записывается в `import_operator_deliveries.rejected_status`, пакет остаётся в `PROCESSING`, следующие пакеты ждут сверки. Чтобы возобновить неизменённую команду после устранения причины отказа, очистите `rejected_status` этой части и `published_at` пакета в одной транзакции. Worker удаляет XLSX из закрытого тома после завершения обработки сообщения. API также удаляет XLSX при ошибке создания записи до начала фиксации транзакции. При аварийном завершении процесса или неизвестном результате фиксации файл может остаться в томе.

Откат последнего применённого пакета фиксирует план в Import DB. API последовательно подтверждает восстановление в Clients, очистку Operator Work и завершение отката в Clients. Если запрос прервался, повтор с исходным `operation_id` продолжает неподтверждённые шаги. Отсутствующий пакет возвращает `404`, более ранний — `409 IMPORT_NOT_LATEST`. Если набор целей очистки изменился, конфликт требует сверки сохранённой команды. См. [контракт отката](../../docs/api/import-operator-work-contract.md#откат-и-выборочная-очистка).

## Доставка ошибок в Errors History

Перед обновлением остановите старый Worker, примените миграцию `0006_errors_outbox` и запустите новый Worker. Новые ошибки сохраняются вместе с готовым запросом в `import_errors_outbox`. У прежних строк время остаётся пустым, их перенос выполняется отдельно.

Установите `IMPORT_ERRORS_HISTORY_URL` в окружении Worker или в его локальном `.env`. Укажите базовый URL, например `http://errors-history:8000`, доступный из контейнера Worker. При пустой переменной исходящие запросы остаются в очереди и будут отправлены после запуска Worker с настроенным URL.

Для локального запуска двух Compose-проектов используйте следующий пример.

1. Из `services/errors-history` запустите `docker compose -p kontur-errors-history up --build -d --wait`.
2. В `services/import-worker/.env` задайте `IMPORT_ERRORS_HISTORY_URL=http://errors-history:8000`. Из каталога Import Worker запустите `docker compose -p kontur-import up --build -d`.
3. Подключите контейнер Worker к сети Errors History командой `docker network connect kontur-errors-history_default $(docker compose -p kontur-import ps -q import-worker)`. После пересоздания контейнера подключите его снова.

После коммита отправитель передаёт одну ошибку за запрос. Повторы используют то же тело с тем же `source_error_id` и датой. При временном сбое интервал повторов растёт до 60 секунд. Состояние видно в `import_errors_outbox` по `attempt_count`, `next_attempt_at` и `delivered_at`. HTTP 409 сохраняется в `rejected_status`. Такая запись остаётся для сверки по `source_error_id`, остальные продолжают доставляться.

## Проверки

```sh
poetry check --lock
poetry sync
poetry run ruff check .
poetry run ruff format --check .
poetry run python -m pytest --cov=import_worker
docker compose -p kontur-import-test -f compose.yaml -f compose.test.yaml run --build --rm import-tests
```

Последняя команда запускает интеграционные тесты на отдельном стенде с PostgreSQL и RabbitMQ. Clients Service в этих тестах заменён HTTP-имитацией. Для запуска проверок с уже поднятыми тестовыми службами задайте `IMPORT_TEST_DATABASE_URL` и `IMPORT_TEST_AMQP_URL`. Перед тестами примените миграции к пустой тестовой Import DB. Тест RabbitMQ использует ту же очередь, что и Worker, поэтому запускайте его на отдельном брокере.

Для проверок outbox отдельно запустите `poetry run python -m pytest tests/test_errors_history.py` с `IMPORT_TEST_DATABASE_URL`. Тесты создают временные БД, поэтому тестовой роли нужно право `CREATE DATABASE`. Они проверяют миграцию, атомарную запись, недоступность и конфликт Errors History через HTTP-имитацию.

Переменные `IMPORT_TEST_CLIENTS_URL` и `IMPORT_TEST_OPERATOR_WORK_URL` включают проверку истории и переноса остатков через HTTP с настоящими сервисами. Используйте отдельные тестовые БД.

# Operator Work Service

Сервис хранит опубликованный пул, назначения и запросы на перезакрепление в PostgreSQL. При запросе на занятого клиента прежнее назначение остаётся активным. Текущий ответственный может отказать в течение часа. После истечения часа сервис применяет запрос, если цикл и назначение актуальны и защита WAIT_DEADLINE не действует. Время берётся из БД. Фоновый обработчик проверяет просроченные запросы каждые пять секунд и продолжает обработку после перезапуска.

## Локальный запуск

В PowerShell из каталога сервиса:

```powershell
$env:OPERATOR_WORK_SERVICE_TOKEN = [guid]::NewGuid().ToString()
docker compose up --build -d
```

API и Swagger доступны на `http://127.0.0.1:8000/docs`. Compose создаёт выделенную БД и применяет миграцию Alembic. Учётные данные PostgreSQL в Compose предназначены для локального запуска.

## Проверка в интерфейсе

В той же PowerShell-сессии перейдите в каталог `frontend` и запустите:

```powershell
$env:OPERATOR_WORK_URL = 'http://127.0.0.1:8000'
$env:OPERATOR_WORK_QUARTER = '2026_Q4'
npm ci
npm run dev
```

1. Войдите администратором, отметьте нужных клиентов в разделе «Список на обзвон» и нажмите «Передать операторам». Публикуются выбранные клиенты.
2. Откройте две независимые браузерные сессии с разными демонстрационными операторами, например `anna.k` и `oleg.p`.
3. В первой сессии возьмите свободного клиента. Во второй откройте его карточку и нажмите «Перезакрепить на себя».
4. В первой сессии появится уведомление с крайним сроком и кнопкой «Отказать». При отказе ответственный сохранится. Если оставить запрос без ответа, через час сервис сменит ответственного. Интерфейс обновляет данные каждые пять секунд.

Next.js передаёт запросы на Python-сервис от имени текущей демонстрационной сессии. После подключения Go Gateway следует передавать реальные UUID и роли из Identity вместо идентификаторов демонстрационных учётных записей. Токен сервиса хранится на серверной стороне. Импорт и полный жизненный цикл рабочего цикла подключаются отдельно.

## API

- `PUT /internal/v1/pool/publication?work_quarter=YYYY_QN` публикует выбранные коды из массива `codes` (до 1000 за запрос). Роль ADMIN. Публикация дополняет пул, повтор сохраняет назначения и сроки. При ошибке изменения всего запроса откатываются.
- `PUT /internal/v1/clients/{code}/publication?work_quarter=YYYY_QN` публикует клиента. Роль ADMIN.
- `GET /internal/v1/pool?work_quarter=YYYY_QN` отдаёт актуальный опубликованный пул.
- `GET /internal/v1/clients/{code}/assignment?work_quarter=YYYY_QN` отдаёт ID активного назначения или null.
- `POST /internal/v1/clients/{code}/take?work_quarter=YYYY_QN` принимает `expected_assignment_id` и UUID `request_id`. При свободном клиенте возвращает 200, при создании запроса 202, при устаревшем назначении или другом конфликте 409. При сетевом повторе используется тот же `request_id`.
- `GET /internal/v1/reassignment-notifications` возвращает входящие и исходящие запросы авторизованного оператора.
- `POST /internal/v1/reassignment-notifications/{request_id}/reject` отклоняет запрос по праву текущего получателя уведомления до истечения часа.

Для внутренних запросов требуются сервисный Bearer-токен и заголовки `X-User-Id` и `X-User-Role`. Настройки сервиса передаются в `OPERATOR_WORK_SERVICE_TOKEN` и `OPERATOR_WORK_DATABASE_URL`.

## Тесты

Укажите `OPERATOR_WORK_TEST_DATABASE_URL` для **отдельной тестовой PostgreSQL**. Тесты применяют миграции и очищают таблицы перед каждым сценарием.

```powershell
poetry install --no-root
poetry run ruff check .
poetry run ruff format --check .
poetry run pytest --cov=operator_work
```


## Сохранение звонка

Из карточки закреплённого клиента откройте звонок и заполните результат. Обещанная дата относится к договорённости, а дата «Ожидание до» включает защиту WAIT_DEADLINE. После сохранения запись доступна в ленте карточки.

API `POST /internal/v1/clients/{code}/events` принимает тип CALL_RESULT, идентификатор назначения из формы и уникальный ID запроса. Повтор с теми же данными возвращает сохранённое событие. При смене ответственного в текущем цикле прежний оператор сохраняет только звонок. Ответ `wait_applied` показывает, установил ли этот запрос срок ожидания.

API `GET /internal/v1/clients/{code}/events` отдаёт ленту с пагинацией. Запрос состояния назначения отдаёт текущий этап и срок. Миграция `20261109_02` применяется при следующем запуске Compose.

## Возврат в пул после ожидания

Настройте `OPERATOR_WORK_CLIENTS_URL` на внутренний адрес Clients. В Compose адрес должен быть доступен из контейнера API. Фоновая проверка обращается к `GET /internal/v1/clients/{kcr_code}` и читает общий остаток `outstanding_documents`. Без настройки URL сервис сохраняет просроченные циклы вне пула.

В дату ожидания по Москве клиент возвращается в пул после подтверждения положительного остатка. Прежнее назначение завершается, а в ленте появляется системная запись. Ноль, ошибка ответа или отсутствие связи не меняют назначение. Проверки повторяются каждые 30 секунд после завершения предыдущего прохода. Если срок или цикл изменился во время проверки, сервис ждёт следующего подходящего прохода.

Прошлый комментарий записывается оператором в опубликованной карточке через `POST /internal/v1/clients/{code}/events` с типом HISTORICAL_COMMENT. В запросе передаются фактическое время с часовым поясом, текст и ID запроса. Сервис сохраняет время внесения и автора из сессии. Общий комментарий без work_quarter отображается в общей ленте и не меняет рабочее состояние.

## Локальная очистка при полном удалении клиента

Доверенный сервис от имени администратора вызывает `POST /internal/v1/data-cleanup`. Тело содержит `operation_id` (UUID), `kcr_code` и `scope: CLIENT`. Ответ со статусом COMPLETED подтверждает очистку Operator Work. Повтор с теми же ID операции, клиентом и инициатором возвращает тот же ответ. Если после очистки клиент опубликован заново, старый запрос не удалит новую работу.

Миграция `20261109_03` добавляет журнал операций без содержимого удалённых записей. Удаление и запись в журнал выполняются в одной транзакции.

## Применение тестового среза к циклам

В Swagger или внутреннем API вызовите `PUT /internal/v1/cycles/apply-snapshot?work_quarter=2026_Q4` от имени ADMIN с сервисным токеном. Пример тела:

```json
{
  "batch_id": "73e34430-2f72-4001-9bed-0d11c70dd272",
  "clients": [
    {"kcr_code": "AAA00412", "outstanding_documents": 3},
    {"kcr_code": "AAA02210", "outstanding_documents": 0}
  ]
}
```

Создаётся неопубликованный цикл для AAA00412. AAA02210 пропускается из-за нулевого остатка. Чтобы передать первого клиента операторам, опубликуйте его в том же квартале отдельным запросом. При повторной отправке пакета сохраните batch_id. Повтор с изменённым содержимым вернёт конфликт.

Миграция `20261109_04` добавляет журнал обработанных пакетов. Тестовый вход принимает готовые общие остатки, а способ доставки из Import и Clients согласуется отдельно.

## Выборочная очистка и контракт Gateway

Миграция `20261109_05` добавляет устойчивые ID циклов, явный текущий цикл и данные для повтора выборочной очистки. Доверенный администратор получает ID через `GET /internal/v1/clients/{code}/cycles`. Для `POST /internal/v1/data-cleanup` с областью QUARTER передаётся исходный квартал документов и точные `cycle_ids` и `event_ids`. Для BATCH передаётся также ID отменяемого пакета. Откат с удалением текущего цикла и оставшейся историей требует `restore` с ID оставшегося цикла, флагом публикации, этапом, UUID ответственного и сроком. Список поддерживаемых этапов и поля запроса описаны во внутреннем OpenAPI.

Gateway должен проверять личность и роль, устанавливать X-User-Id и X-User-Role и добавлять внутренний сервисный Bearer-токен. Пул, назначение и лента имеют типизированные ответы в OpenAPI. Реальные маршруты и доставка пакетов проверяются после подключения сервисов.

Import Worker как координатор проверяет, что откатывается последний допустимый пакет, и определяет связь событий с исходными данными. Operator Work проверяет принадлежность указанных ID клиенту, происхождение удаляемых циклов и полноту списка событий.

Примеры запросов, повторов и восстановления приведены в [контракте Import Worker и Operator Work](../../docs/api/import-operator-work-contract.md).

При пакетах больше 1000 клиентов сохраняйте исходный batch_id и отправляйте части с отдельным delivery_id по [контракту](../../docs/api/import-operator-work-contract.md#большие-пакеты). Operator Work подтверждает каждую часть. Для локального запуска применяется миграция 20261111_07.

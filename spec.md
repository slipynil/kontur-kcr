# Technical Specification (spec.md): Веб-сервис «Контур КЦР»

**Версия спецификации:** 1.4
**Контекст проекта:** Сервис контроля передачи оригиналов документов корпоративными клиентами КЦР (АО «СКБ Контур»).  
**Связанные документы:**
- Правила ИИ и кодогенерации: `AGENTS.md`
- Архитектурная диаграмма: `docs/c4-l2-container-diagram.html`
- Архитектурные решения: `docs/adr/`
- Спецификации API (OpenAPI): `docs/api/`
- Модель данных и DDL: `docs/db/`
- Первичное бизнес-ТЗ: `docs/requirements/ТЗ.docx`

**Обязательная функциональность:** импорт клиентов и срезов без дублей; хранение истории изменения статуса передачи документов и автоматический расчёт динамики; общая таблица с фильтрами; атомарное взятие и перезакрепление клиента при отсутствии действующего ожидания срока оператора; фиксация события «звонок»; карточка клиента с полной историей взаимодействия; поиск по коду КЦР и ИНН; разграничение ролей.

**Актуализация от 05.11.2026:** комментарии заказчика Vera V от 03.11.2026 к UC-08–UC-11 (таблица `use_cases_spreadsheet.xlsx`, A11:A14; хранится вне репозитория) имеют приоритет над более ранним ТЗ и описаниями сценариев в ADR. UC-08, UC-10 и UC-11 исключены. UC-09 допускает перезакрепление клиента любым оператором при отсутствии действующего ожидания срока оператора.

**Уточнения от 05.11.2026:** квартал выбирается при загрузке; непереданные документы переносятся без потери и двойного счёта; задержка от двух кварталов длительная; WAIT_DEADLINE защищает ответственного до даты оператора, в том числе через границу квартала. Подробные правила — §1.3.

## 1. Системный контекст и архитектурные ограничения

### 1.1 Распределение сервисов (C4 Model Level 2 Alignment)
Система представляет собой микросервисную архитектуру, логически и технологически разделённую согласно `AGENTS.md`:

1. **Gateway / Identity Service (Go):**
   - **Зона ответственности:** Единственная точка входа (API Gateway), аутентификация/авторизация (JWT/Sessions), разграничение ролей RBAC (`ADMIN` / `OPERATOR`), проксирование REST/gRPC запросов к внутренним сервисам (включая агрегацию карточки клиента из Clients Service и Operator Work Service), контроль CORS и таймаутов.
2. **Clients Service (Python):**
   - **Зона ответственности:** Реестр клиентов (Код КЦР, ИНН, КПП, признаки через справочник тегов), управление статусами клиентов, хранение срезов по кварталам и **журнала истории изменения статуса передачи документов**, автоматический расчёт динамики, поиск по Коду КЦР и ИНН.
3. **Import Worker (Python):**
   - **Зона ответственности:** Фоновая асинхронная обработка Excel-файлов (`.xlsx`), парсинг, валидация по правилам КЦР (включая дедупликацию), логика сохранения/накопления срезов по кварталам без дублей, формирование отчёта об импорте и выявление проблемных строк, откат импорта.
4. **Operator Work Service (Python):**
   - **Зона ответственности:** Закрепление клиентов за операторами (атомарное, без конфликтов), этапы работы, лента событий карточки клиента (звонки, комментарии, письма, претензионная работа), формирование списков на обзвон, работа с шаблонами писем, логика отбора базы под квоты.
5. **Assistant Service (Python):**
   - **Зона ответственности:** ИИ-ассистент через облачный API стороннего провайдера. Конкретные функции и критерии приёмки согласуются отдельно; ответы опираются на факты сервиса.

### 1.2 Критические правила безопасности и бизнес-ограничения
- **ИИ-провайдер:** облачный API стороннего провайдера. Внешняя передача контекста для ИИ допускается по согласованному сценарию; прежнее требование только локальной модели отменено. Это не разрешает публикацию выгрузок в открытом доступе.
- **Идентификатор клиента:** Первичным бизнес-ключом системы является **`Код КЦР`** (строка/ID). Один ИНН может иметь несколько уникальных Кодов КЦР.
- **Терминологический бан:** В API, интерфейсах, БД и комментариях ЗАПРЕЩЕНО использовать слова `долг`, `задолженность`, `должник`. Допустимы только `неотправленные документы` / `непереданные оригиналы документов`.
- **Импорт без дублей:** Один срез на пару (`kcr_code`, `quarter`) — повторная загрузка того же квартала обновляет только число непереданных документов и никогда не создаёт дубликат записи. Дубликаты строк внутри одного листа файла отсекаются при импорте.
- **Сохранность историчности:** Общее количество документов за квартал («Всего документов») фиксируется при первой загрузке квартала. При последующих срезах за этот же квартал меняется только число непереданных документов.
- **История изменения статуса передачи документов:** Каждое новое наблюдение, включая неизменный остаток, фиксируется в журнале (значение, дата среза, пакет импорта). Журнал — основа расчёта динамики; обычные записи не редактируются. Удаление допускается при откате последнего пакета и ручном каскадном удалении.
- **Race Condition Protection:** Фиксация клиента за оператором при нажатии «Взять в работу» должна быть атомарной на уровне БД (SELECT FOR UPDATE / ACID-транзакция / уникальный индекс активного закрепления).

### 1.3 Квартал, перенос документов и ожидание срока

- При загрузке администратор явно выбирает квартал, за который велись данные: `selected_quarter` в формате `YYYY_QN`. Он определяет квартал наблюдения и квартальный цикл обзвона `work_quarter`. Дата файла, дата загрузки и имя листа не назначают квартал автоматически. Имя листа может быть подсказкой и проверкой соответствия выбранному кварталу.
- Отчётные периоды только квартальные. Старые годовые/составные агрегаты не преобразуются в кварталы и не загружаются как самостоятельный период; используются квартальные листы. По выбранному кварталу добавляется информация, включая исторические загрузки; загрузка старого квартала не переключает текущую работу назад и не заменяет более свежие наблюдения старым срезом.
- `quarter` документов сохраняет исходный квартал их возникновения. Непереданные документы продолжают учитываться в следующем квартале до передачи. Перенос — продолжение учёта того же остатка, без создания второй копии и повторного суммирования. В карточке видны исходный период и текущий остаток; общее количество непереданных — сумма остатков по уникальным исходным периодам.
- Длительная задержка (`LONG_DELAY_2Q`) — непереданные документы сохраняются два последовательных квартала и более. Один квартал — обычная задержка. Уменьшение остатка не обнуляет длительность оставшихся документов. Пропуск данных не доказывает ни сдачу документов, ни отсутствие задержки.
- Оператор назначает конкретную дату ожидания `wait_until` при переводе в `WAIT_DEADLINE`. Пока дата не наступила, сохраняются этот этап и ответственный. Другой оператор получает `409 CLIENT_WAIT_DEADLINE_ACTIVE`. Новый квартал и новый срез, в том числе с частичной передачей документов, защиту не снимают.
- При создании нового квартального цикла с остатком проверяется незавершённое ожидание предыдущего цикла. Если срок ещё не наступил, в новый цикл переносятся `WAIT_DEADLINE`, тот же ответственный и исходный срок; сохраняется ссылка `wait_source_work_quarter`. Дата не продлевается автоматически. Предыдущие события и закрепления остаются в истории.
- По наступлении срока (`business_date >= wait_until`) защита заканчивается. При наличии непереданных документов клиент доступен для обзвона и перезакрепления: актуальное состояние — `POOL` без активного ответственного. Это нормализуется при чтении/изменении состояния либо фоновым обработчиком; отдельная пользовательская очередь «Сегодня нужно» не вводится. Повторный запрос не дублирует переход или события. Если остатка нет, клиент не возвращается в обзвон; автоматическое закрытие работы без отдельного правила не добавляется.
- Если действующего ожидания нет, новый квартальный срез с остатком создаёт цикл `POOL` без ответственного. Повторная обработка того же квартала не сбрасывает уже начатую работу. В текущем представлении один ответственный на клиента; сохранённые закрепления старых циклов показываются как история.
- Пустая или отсутствующая запись не равна нулю. При заполнении нового среза недостающие значения берутся из предыдущих данных клиента, сохраняется происхождение значения, клиент получает `needs_review=true` и список полей проверки. Явные `0` и `false` считаются новыми значениями. Обязательные значения без предыдущих данных попадают в ошибки; клиент не создаётся с выдуманным количеством документов.

## 2. Модель данных и сущности (Domain Model)

Полные DDL и связи — в `docs/db/`; между БД сервисов физические FK отсутствуют, связи логические.

### 2.1 Сущность `User` (Пользователь) — Identity DB
- `id`: UUID (PK)
- `login`: String (Unique)
- `password_hash`: String
- `role`: Enum (`ADMIN`, `OPERATOR`)
- `is_active`: Boolean
- `created_at`: Timestamp

### 2.2 Сущность `Client` (Карточка клиента КЦР) — Clients DB
- `kcr_code`: String (PK / Unique Identifier)
- `inn`: String (Indexed)
- `kpp`: String
- `organization_name`: String
- `status`: Enum (`ACTIVE`, `INACTIVE`)
- `is_blocked`: Boolean
- `manager_name`: String
- `contacts`: JSONB
- `needs_review`: Boolean (есть унаследованные/неполные данные)
- `inherited_fields`: JSONB (поле → квартал/пакет/дата исходного значения)
- `raw_work_status`: String (исходный рабочий статус из выгрузки; хранится для истории и разбора, в UI не показывается)
- `source`: Enum (`REGISTRY`, `SNAPSHOT`) — откуда создан клиент
- **Признаки (Tags):** связь M:N со справочником тегов (`VIP`, `NOVICE`, `INTEGRATOR`, `TECH_PARTNER`, `MPP`, `DO_NOT_WORK`); новые признаки добавляются строкой справочника, без миграции схемы
- `created_at`, `updated_at`: Timestamp

Закрепление за оператором и этап работы — сущности Operator Work DB (§2.7, §2.8), не поля клиента.

### 2.3 Сущность `QuarterSnapshot` (Актуальный срез квартала) — Clients DB
- `kcr_code` + `quarter`: составной PK; `quarter`: String (`2026_Q1`, `2026_Q2`, …)
- `total_documents`: Integer (Запоминается при первом импорте квартала, далее не меняется)
- `unsubmitted_documents`: Integer (Обновляется каждым новым срезом того же квартала)
- `import_batch_id`: UUID (логическая ссылка на `ImportBatch.id`; последний пакет, менявший запись)
- `snapshot_date`: Date (дата последней загрузки)
- `created_at`, `updated_at`: Timestamp

Поле `last_observation_quarter` — квартал наблюдения, выбранный при загрузке. `quarter` — исходный период документов; перенос не дублирует запись. Одна запись на (`kcr_code`, `quarter`) — актуальное состояние; логика upsert см. §3.2.

### 2.4 Сущность `QuarterSnapshotHistory` (Журнал истории изменения статуса передачи документов) — Clients DB
Журнал наблюдений: одна запись на каждый новый срез, включая неизменный остаток; повтор того же наблюдения идемпотентен. Поле `observation_quarter` хранит выбранный квартал загрузки.
- `id`: UUID (PK)
- `kcr_code`: FK -> `Client.kcr_code`
- `quarter`: String
- `unsubmitted_documents`: Integer (значение после изменения)
- `import_batch_id`: UUID (логическая ссылка на пакет, вызвавший изменение)
- `snapshot_date`: Date (дата среза)
- `created_at`: Timestamp

Первая загрузка квартала создаёт и запись `QuarterSnapshot`, и первую запись журнала. На основе журнала рассчитывается динамика (§3.3); использование в функциях ИИ согласуется отдельно (§3.4).

### 2.5 Сущность `ClientEvent` (Лента событий / Звонки / Комментарии) — Operator Work DB
- `id`: UUID (PK)
- `kcr_code`: String (логическая ссылка на `Client.kcr_code`)
- `work_quarter`: String / Nullable (квартал обзвона; NULL для старого комментария без установленного цикла)
- `author_id`: FK -> `User.id`
- `event_type`: Enum (`CALL_RESULT`, `HISTORICAL_COMMENT`, `EMAIL_SENT`, `STAGE_CHANGE`, `CLAIM_UPDATE`, `OPERATOR_ASSIGN`)
- `call_result`: Enum (`AGREEMENT`, `REFUSAL`, `NO_ANSWER`, `WRONG_NUMBER`) (Nullable, только для `CALL_RESULT`)
- `stage`: Enum / Nullable (цель события STAGE_CHANGE)
- `wait_until`: Date / Nullable (срок оператора на момент события; обязателен для WAIT_DEADLINE)
- `promised_date`: Date (Nullable)
- `comment_text`: Text
- `historical_event_date`: Timestamp (Заполняется оператором, если вносится прошлый комментарий)
- `created_at`: Timestamp

Обычная запись ленты append-only; каскадное удаление клиента/квартальных данных и rollback удаляют связанную операторскую работу по §3.2.

### 2.6 Сущность `ImportBatch` (Журнал импортов) — Import DB
Один загруженный файл = один пакет.
- `id`: UUID (PK)
- `uploaded_by`: FK -> `User.id`
- `selected_quarter`: String (обязательный выбор администратора)
- `import_type`: Enum (`REGISTRY`, `SNAPSHOT`)
- `snapshot_date`: Date
- `filename`: String
- `status`: Enum (`PROCESSING`, `COMPLETED`, `ROLLED_BACK`, `FAILED`)
- `total_rows`, `success_count`, `error_count`: Integer
- `created_at`, `completed_at`: Timestamp

Детальные строки ошибок хранятся в таблице `ImportErrors` (`batch_id`, `sheet`, `row_number`, `kcr_code`, `reason`) — основе виджета скачивания `.xlsx` с ошибками (§4.1). Для отката пакета Worker фиксирует undo-информацию (`ImportBatchUndo`: какие записи (`kcr_code`, `quarter`) пакет создал/обновил и каким было значение до).

### 2.7 Сущность `ClientAssignment` (Закрепление за оператором) — Operator Work DB
- `id`: UUID (PK)
- `kcr_code`: String (логическая ссылка)
- `work_quarter`: String (часть ссылки на квартальный цикл §2.9)
- `operator_id`: FK -> `User.id`
- `assigned_at`: Timestamp
- `released_at`: Timestamp (Nullable; NULL = активное закрепление; при перезакреплении завершает прежнее закрепление)
- `released_by`: UUID (Nullable; оператор, выполнивший перезакрепление)

Активное закрепление максимум одно внутри квартального цикла. При действующем WAIT_DEADLINE сохраняется тот же ответственный, включая новый квартал; назначение нового цикла связано с исходным ожиданием. Проверка `business_date < wait_until`, смена закрепления и запись события атомарны. История сохраняется, кроме явно разрешённого каскадного удаления. Отдельных действий UC-10/UC-11 нет.

### 2.8 Сущность `ClientStage` (История этапов) — Operator Work DB
- `id`: UUID (PK)
- `kcr_code`: String (логическая ссылка)
- `work_quarter`: String (часть ссылки на квартальный цикл §2.9)
- `stage`: Enum (`POOL`, `IN_WORK`, `WAIT_DEADLINE`, `CLAIM`, `CLOSED`)
- `changed_by`: UUID
- `changed_at`: Timestamp
- `comment`: Text (Nullable)

Актуальный этап — последняя запись внутри пары (`kcr_code`, `work_quarter`). Смена этапа дублируется событием `STAGE_CHANGE`, взятие в работу — `OPERATOR_ASSIGN` в ленте событий.

### 2.9 Сущность `ClientWorkCycle` (Участие в квартальном обзвоне) — Operator Work DB
- `kcr_code` + `work_quarter`: составной PK; `work_quarter`: String (`2026_Q1` и т. п.).
- `source_import_batch_id`: UUID / Nullable (пакет, создавший цикл по срезу; логическая ссылка на Import DB).
- `created_at`: Timestamp.

Цикл принадлежит выбранному кварталу загрузки. Поля `wait_until` (DATE, nullable) и `wait_source_work_quarter` (TEXT, nullable) сохраняют срок оператора и источник ожидания. При новом квартале с остатком и ещё действующем ожидании создаётся WAIT_DEADLINE с тем же оператором и сроком; иначе POOL без ответственного. После срока при остатке клиент возвращается в доступный пул. Повторные загрузки не сбрасывают начатую работу. Старый квартал не становится текущим при поздней загрузке.

## 3. Спецификация микросервисов и API

### 3.1 Gateway / Identity Service (Go)
**Обязанности:**
- `POST /api/v1/auth/login` — аутентификация.
- `GET/POST /api/v1/users` — CRUD пользователей (только `ADMIN`).
- Проксирование запросов в Python-микросервисы с проверкой Bearer JWT и роли.

---

### 3.2 Import Worker (Python)

1. Администратор выбирает тип файла (`REGISTRY` / `SNAPSHOT`) и обязательный `selected_quarter`; для среза задаётся дата наблюдения `snapshot_date`. Файл реестра может содержать только профиль; срез обновляет квартальные значения. Годовые и составные листы из старого Excel пропускаются с понятной причиной, используются квартальные данные.
2. Отсекаются итоги, ошибки ячеек Excel (включая `#N/A`), строки без кода КЦР, дубликаты внутри листа, неизвестные коды среза и дробные счётчики. Значение `111.0` является целым. Ошибка строки не останавливает корректные строки.
3. Недостающие поля дополняются из последних известных данных с отметкой `needs_review` и происхождением. При новом квартале неизменившийся остаток старого периода продолжает учитываться под исходным `quarter`; он не становится новым комплектом документов. Явное новое значение заменяет прежнее; пустота не очищает его.
4. Первая загрузка исходного квартала фиксирует `total_documents`; повторный срез может не содержать total. Новый срез сохраняется в истории даже при прежнем остатке. Повтор того же файла/наблюдения не создаёт историю повторно. Исторический срез дополняет историю выбранного квартала; актуальное состояние определяется датой наблюдения, а не порядком загрузки.
5. После применения Clients Service выдаёт актуальные остатки; Operator Work обновляет пул по §1.3 и сохраняет действующий WAIT_DEADLINE вместе с ответственным. Пакет завершён только после согласованного обновления клиентских данных и работы операторов. Повторы идемпотентны.
6. `POST /api/v1/imports/{batch_id}/rollback` отменяет только последний применённый и ещё не отменённый пакет в системе. Более ранний пакет возвращает `409 IMPORT_NOT_LATEST`. Созданные данные удаляются, обновлённые восстанавливаются из undo, удаляется история пакета. Связанная с удалёнными данными начатая работа операторов также удаляется, а не сохраняется как действующая задача.
7. Администратору доступны ручное удаление клиента целиком и удаление данных выбранного квартала. При удалении клиента из всех БД убираются его срезы, события, пулы, этапы, закрепления и сроки. При удалении квартальных данных убираются связанные с ними записи работы, переносы и производные остатки; прочие данные клиента сохраняются. Нельзя оставить действующее закрепление или ожидание без исходных данных. Объём удаления определяется выбранным объектом, а не всеми клиентами оператора.
8. Все удаления и rollback согласованно выполняются сервисами через API, с идемпотентными повторами. Завершённым удаление считается после очистки всех затронутых хранилищ и кэшей. Запрета удаления из-за уже начатой работы нет. Технический журнал хранит автора, время, объект и результат операции, но не удалённое содержимое.

### 3.3 Clients Service & Operator Work Service (Python)
**Обязанности:**
- `GET /api/v1/clients` — общая таблица (реестр) с параметрами фильтрации:
  - `search` (Код КЦР / ИНН)
  - `dynamics` (`REDUCING`, `NO_CHANGE`, `GROWING`, `ALL_SUBMITTED`)
  - `duration` (`FIRST_TIME`, `REPEATED`, `LONG_DELAY_2Q`)
  - `tags` (`VIP`, `NOVICE`, `INTEGRATOR`, `TECH_PARTNER`, `MPP`, `DO_NOT_WORK`)
- `GET /api/v1/clients/{kcr_code}` — карточка клиента с полной историей взаимодействия: профиль и теги, актуальные срезы по кварталам, закрепление, этап; лента событий и журнал изменений статуса передачи документов получаются подчинёнными эндпоинтами (агрегация данных Clients Service и Operator Work Service выполняется Gateway).
- `GET /api/v1/clients/{kcr_code}/events` — лента событий (пагинированная, свежие первыми).
- `POST /api/v1/clients/{kcr_code}/take` — взятие или перезакрепление на текущего оператора, query `work_quarter` обязателен.
  - Другой ответственный не блокирует операцию, если нет действующего ожидания.
  - Пока `business_date < wait_until`, сохраняются WAIT_DEADLINE и ответственный; другой оператор получает `409 CLIENT_WAIT_DEADLINE_ACTIVE`, даже если квартал сменился.
  - С наступлением даты при остатке документов клиент доступен в POOL; повтор запроса текущего ответственного не дублирует историю.
  - Изменение исторического цикла запрещено (`409 INVALID_STATE`), кроме установленных операций удаления. Дата трактуется в бизнес-часовом поясе Europe/Moscow.
- `POST /api/v1/clients/{kcr_code}/events` — добавление события (звонок, прошлый комментарий с ручной датой `historical_event_date`).

**Автоматический расчёт динамики.** Динамика клиента рассчитывается автоматически по журналу истории изменения статуса передачи документов (§2.4): берутся две последние записи наблюдений выбранного исходного квартала документов (`prev` -> `last`):
- `ALL_SUBMITTED` — `last.unsubmitted_documents = 0` (все переданы);
- `REDUCING` — число непереданных уменьшилось;
- `NO_CHANGE` — не изменилось;
- `GROWING` — выросло;
- не определена (`null`) — по последнему кварталу единственная запись журнала (нет сравнимого предыдущего наблюдения; не подменяет категорию FIRST_TIME).

Пересчёт выполняется при каждом добавлении записи журнала (импорте); результаты используются фильтром `dynamics`, цветовой индикацией (§4.2).

### 3.4 Assistant Service (Python)

Используется облачный API стороннего провайдера. Провайдер, модель, набор функций, возможные изменяющие действия и приёмочные критерии обсуждаются отдельно. Имеющиеся summary/filter-query/chat контракты сохраняются как предложения; они не утверждают обязательный набор функций MVP. Работа с текущим WAIT_DEADLINE учитывает дату, а не только принадлежность к прошлому кварталу. Удалённые данные исключаются из контекста и кэшей ассистента.

## 6. Контрольные сценарии

1. Выбор квартала при загрузке важнее имени и даты файла; годовой лист не становится самостоятельным периодом.
2. Непереданные документы Q1 видны в Q2 с исходным периодом Q1 и учитываются один раз; частичная передача уменьшает остаток. Во втором квартале непрерывной задержки появляется LONG_DELAY_2Q.
3. WAIT_DEADLINE до срока защищает ответственного от перезакрепления. При новом квартальном срезе до этой даты сохраняются оператор, этап и дата, а не создаётся свободный клиент.
4. При наступлении даты и остатке документов клиент доступен в POOL без закрепления; перезакрепление возможно. Повторное чтение не создаёт дубликаты перехода. При нулевом остатке клиент не возвращается в обзвон.
5. Пустые поля нового среза наследуются, отмечаются needs_review и имеют источник. Явные ноль/false не заменяются старыми данными. Нет предыдущих обязательных данных — ошибка строки.
6. Исторический квартал и более ранняя дата среза добавляют историю без переключения текущей работы назад. Повтор файла не создаёт дублей; новый срез с тем же числом сохраняет наблюдение.
7. Откат последнего пакета восстанавливает данные и очищает связанную удалённую работу операторов. Откат более раннего пакета запрещён.
8. Ручное удаление клиента/квартальных данных очищает связанные пулы, назначения, ожидания и события даже после начала работы; другие клиенты оператора не затрагиваются.
9. Ассистент использует облачный API и факты сервиса; конкретные сценарии проверки утверждаются после отдельного согласования функций ИИ.

## 7. Вопросы, отложенные до отдельного согласования

- Источник даты подключения/признака «Новичок» обсуждается с заказчиком позже; дата первого импорта не подменяет дату подключения.
- Конкретные функции ИИ, провайдер, модель, инструменты и объём MVP согласуются отдельно. Существующие API ИИ — предложения, а не зафиксированный обязательный набор.
- Точный расчёт категорий FIRST_TIME/REPEATED, общий приоритет цвета при разных состояниях периодов, глубина претензий/санкций/писем/вложений/импорта старой истории и поведение закрытия при нулевом остатке пока не утверждены.
- Низкоуровневый межсервисный протокол применения, удаления и восстановления после сбоя должен быть завершён перед реализацией; бизнес-правила последнего rollback и каскадной очистки уже определены.

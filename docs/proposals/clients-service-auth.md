# Предложение проверки межсервисных вызовов Clients

Статус: **Proposed**. По ответу пользователя от 07.11.2026 подготовлено только предложение. Проверка токенов не добавлена в код, способ необходимо согласовать с разработчиком Gateway и владельцем Import.

## Предлагаемый вариант для первого стенда

У каждого вызывающего сервиса отдельный случайный секрет. Клиент передаёт `Authorization: Bearer <service-token>` во внутреннюю сеть по защищённому каналу. Clients определяет вызывающий сервис и проверяет разрешённую группу маршрутов. Токен — машинная идентичность, а не пользовательский JWT. Клиентские токены входа в Gateway не должны приниматься Clients как сервисные.

| Вызывающий сервис | Предлагаемый доступ |
|---|---|
| Gateway | Реестр, карточка, история |
| Import / координатор | Apply, rollback, удаление |
| Operator Work | Чтение клиентских данных — требует отдельного согласования |
| Assistant | Доступ определяется после согласования ИИ-функций |

Пользовательские роли, пул оператора и право административного действия проверяет Gateway/координатор. requested_by/uploaded_by формируются из доверенного контекста, а не из произвольного публичного JSON. Сервисный токен не заменяет эту проверку. Особо нужно согласовать ограничение операторов их пулом до пагинации, а не скрывать строки уже полученной страницы.

## Детали, которые нужно утвердить до кода

- Источник секретов окружения/хранилища секретов, длина, выдача каждому участнику и процедура ротации. Секреты не включаются в Git, примеры, журналы и OpenAPI.
- Сравнение токенов без утечки по времени; общий отказ без раскрытия ожидаемого значения. Нет/неверный токен — 401, известный сервис без права маршрута — 403.
- Защищённый канал между сервисами, сетевые ограничения и недоступность внутреннего API из браузера напрямую.
- Нужно ли разрешать короткое перекрытие старого и нового токена при ротации.
- Единый request ID, правила переноса пользовательского контекста и сопоставление requested_by/uploaded_by с подтверждённым автором.
- Должен ли Import также читать реестр; как Operator Work получает данные; требуется ли отдельный сервисный токен для каждого экземпляра.

Альтернативы — подписанные короткоживущие сервисные JWT или mTLS. Выбор не сделан. Текущие переключатели CLIENTS_ENABLE_* только открывают локальные маршруты и не являются механизмом аутентификации. До согласования и реализации внутренние бизнес-маршруты на общем стенде открывать нельзя.

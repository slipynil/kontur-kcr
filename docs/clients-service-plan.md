# План разработки Clients Service

Дата: 07.11.2026. Основание: spec.md 1.7, ТЗ и ADR-0003. Этот документ — рабочий план для последующего выполнения агентом. Пользователь разрешил начать код. Первый этап — каркас сервиса и миграции Clients DB; межсервисные технические решения ещё требуют согласования.

## Результат разработки

Самостоятельно запускаемый Python-сервис с собственной PostgreSQL БД, принимающий нормализованные данные Import и отдающий реестр, карточки и историю Gateway. Реализация должна подтверждать квартальные правила интеграционными тестами. Gateway / Identity ведёт другой разработчик.

## Границы

- Clients: профили, теги, исходные кварталы, актуальные остатки, журнал наблюдений, происхождение полей, поиск, фильтры, динамика, категории задержки, локальное восстановление и удаление.
- Import: Excel, ошибки строк, пакеты, глобальный порядок применения/отката и координация операций.
- Operator Work: циклы, пулы, звонки, назначения, сроки, сохранение общей истории при квартальном удалении.
- Gateway: пользовательская авторизация, публичные маршруты и агрегация карточки. Внутренние поля ожидания удалены из Clients API.
- Не включать ИИ, парсер Excel, интерфейс, управление пользователями и миграции чужих БД в Clients.

## Этап 1. Завершить контракты до реализации

1. Сверить внутренние и публичные схемы: поля nullable, обязательные значения, структура контактов, строковые КЦР/ИНН/КПП, ошибки, ограничения размеров запросов.
2. Согласовать с разработчиком Gateway механизм проверки сервисных вызовов, доверенные заголовки пользователя/роли, request ID, таймауты, формат ошибок. Не предполагать, что произвольным входным заголовкам можно доверять.
3. Зафиксировать quarter документов отдельно от work_quarter. По ADR-0005 без quarter сравниваются текущий календарный квартал и предыдущий; отсутствие одного периода даёт dynamics=null. Проверить фильтрацию списка по периоду, остатку и проценту, которой требует ТЗ.
4. Согласовать фильтры, зависящие от Operator Work: фильтрация по оператору/этапу должна предшествовать пагинации и подсчёту total. Не фильтровать только уже полученную страницу Clients.
5. Определить стабильный порядок выдачи, правила поиска и сочетания тегов, пагинацию полной истории. Текущий limit без продолжения недостаточен для полной истории.
6. Определить идентичность наблюдения между пакетами и внутри повторного запроса. Новый срез с тем же остатком сохраняется; повтор доставки не порождает REPEATED. Решить порядок нескольких исходных кварталов одного клиента в одном пакете: порядок строк не должен искусственно менять категорию.
7. Спроектировать apply/rollback/delete: координатор Import, ключ операции, частичные ошибки строк, состояние операции, повтор после таймаута, атомарное получение undo владельцем данных, восстановление после сбоя. Не читать чужую БД и не обещать распределённую ACID-транзакцию.
8. Согласовать адресацию квартального удаления: исходный период не равен циклу обзвона. Сохранять другие периоды и общие события; проверить, как исключить удалённые данные из агрегатов и кэшей.
9. Определить последовательность ручного удаления и последующего rollback: по выбору пользователя откат восстанавливает также данные, удалённые после импорта. Правило зафиксировано в ADR-0006.

Результат: согласованные OpenAPI, примеры запросов/ошибок и новый ADR для технических решений. Старые ADR не редактировать. Не выдавать проектные предложения за утверждённые договорённости.

## Этап 2. Каркас и модель данных

1. Повторно проверить состояние репозитория, ветку и инструкции; сохранить чужие изменения. До кода поискать готовые функции и инфраструктуру.
2. Создать services/clients; выбрать и закрепить совместимые версии утверждённого стека.
3. Разделить HTTP-слой, прикладные операции, расчёты и работу с PostgreSQL без лишних абстракций.
4. Добавить конфигурацию окружения, безопасные журналы без контактов/сырых выгрузок, health/readiness и корректное закрытие соединений.
5. Подготовить Dockerfile, локальную БД и инструкцию запуска.
6. Сначала уточнить spec.md и docs/db, затем создать Alembic-миграции только Clients DB. DDL — исходная схема, не готовая миграционная история.
7. Предусмотреть данные для стабильного порядка исправлений одной даты, идемпотентности, восстановления профилей/тегов/происхождения. Проверить ограничения и индексы по реальным запросам.

Готовность: сервис запускается с чистой БД, миграции воспроизводимы, readiness отражает доступность БД; отсутствует зависимость запуска от готового Gateway.

## Этап 3. Применение нормализованных данных

1. REGISTRY создаёт/обновляет профиль; SNAPSHOT неизвестного КЦР возвращает ошибку строки согласно ТЗ.
2. Сохранять total_documents при первом импорте исходного квартала; повторные импорты не меняют его.
3. Сохранять каждый новый срез и текущее состояние отдельно. Упорядочивать по дате наблюдения и согласованному порядку исправлений при равенстве дат.
4. Наследовать отсутствующие значения с источником. Явные 0/false сохранять; отсутствие строки не считать передачей документов. Наследование остатка — только для того же исходного периода, не копирование количества в новый квартал.
5. Снимать предупреждения только по реально обновлённым явным полям; пересчитывать общую метку, сохраняя историю происхождения.
6. Атомарно фиксировать изменения и сведения, необходимые для undo, по согласованному протоколу. Обеспечить повтор после потери ответа без повторной записи.
7. Проверить конкурентные запросы и изоляцию разных клиентов. Файлы и Excel-библиотеки этому сервису не нужны.

## Этап 4. Чтение и расчёты

1. Реализовать поиск по КЦР/ИНН, согласованные фильтры, стабильную пагинацию и total.
2. Реализовать карточку и полную историю исходного квартала. Суммировать остатки по всем уникальным исходным кварталам независимо от лимита возвращаемых срезов.
3. Рассчитывать динамику между актуальными остатками выбранного и предыдущего исходного квартала по ADR-0005, отдельно от категории задержки клиента.
4. Реализовать FIRST_TIME → REPEATED → LONG_DELAY_2Q с приоритетом длительности; полный ноль завершает непрерывный период. Частичное уменьшение и отсутствие данных не завершают период.
5. Учитывать исправления и исторические загрузки при пересчёте; не использовать время поступления старого файла как новый квартал работы.
6. Не возвращать значения оператора из Clients; согласовать примеры агрегации с разработчиком Gateway.

## Этап 5. Восстановление и удаление

1. Проверять право на последний rollback через согласованный протокол Import; Clients самостоятельно не определяет глобальный последний пакет по своим локальным строкам.
2. Восстанавливать профиль, теги, текущие значения, историю и предупреждения; повтор rollback не должен повторно менять состояние.
3. Удалять клиентские данные выбранного исходного квартала, пересчитывать показатели, сохраняя другие кварталы.
4. Не удалять общий звонок/срок/цикл другого квартала из-за удалённого исходного периода. Реальную межсервисную проверку выполнить при наличии Operator Work.
5. Полное удаление клиента выполнять отдельно; итоговый успех выдавать только после согласованного завершения затронутых сервисов. Проверить восстановление операции после частичного сбоя.

## Этап 6. Проверки и передача

Тестировать расчёты отдельно и операции на настоящем PostgreSQL. Заглушки соседних сервисов проверяют контракт, но не заменяют сквозную интеграцию.

| Сценарий | Ожидаемый результат |
|---|---|
| Один ИНН, разные КЦР | Независимые клиенты |
| Повтор пакета и потеря ответа | Нет повторных изменений и наблюдений |
| Новый срез с прежним остатком | Новое наблюдение сохраняется |
| Исправление той же даты | Актуально последнее исправление; откат восстанавливает предыдущее |
| Более ранний срез загружен позже | Дополняет историю, не затирает актуальное |
| Q1 переносится в Q2 | Остаток считается один раз под Q1 |
| Пустота против 0/false | Наследование только пустоты; явные значения принимаются |
| Заполнено одно из двух унаследованных полей | Снято одно предупреждение; общая метка остаётся |
| FIRST_TIME, следующий срез, второй квартал | REPEATED, затем LONG_DELAY_2Q |
| Остаток положительный → полный ноль → положительный | Новый FIRST_TIME |
| Частичная передача или пропуск данных | Непрерывный период не сбрасывается |
| Удаление Q1 при общей работе по Q1/Q2 | Q2 и общая история сохранены |
| Два одновременных импорта | Стабильное актуальное состояние и корректный undo |
| Удаление, затем rollback | Поведение соответствует согласованному решению, восстанавливаются удалённые после пакета данные в состоянии до импорта |

Подготовить синтетические примеры без публикации рабочих выгрузок, команды запуска и тестирования, примеры HTTP, список известных ограничений и результаты проверок. Не заявлять готовую интеграцию, если соседние сервисы заменены заглушками.

## Порядок небольших PR

1. Документы и согласованные технические контракты.
2. Каркас, локальный запуск и миграции Clients DB.
3. Профили/теги и применение срезов с идемпотентностью и происхождением.
4. Чтение, фильтры и расчёты.
5. Локальный rollback и квартальное/полное удаление.
6. Межсервисная интеграция и проверка восстановления после сбоев.

Каждый PR содержит необходимые тесты своего поведения. Не объединять изменение чужих сервисов с базовым запуском Clients. Коммиты, push и PR выполняются по отдельному поручению пользователя.

## Состояние реализации

Этап каркаса завершён: FastAPI health endpoints, пул SQLAlchemy, миграции, зависимости, Dockerfile и Compose. Этап локального применения реализован по ADR-0004: профили/теги, квартальные срезы, история, происхождение полей, частичный приём строк, идемпотентность batch_id, результат и undo одной транзакцией. Маршрут apply по умолчанию отсутствует; для изолированной разработки доступен явный переключатель.

Проверки на переносимом PostgreSQL 17.11: 75 тестов прошли без пропусков. Включены upgrade/downgrade/upgrade, исправления одной даты, исторические даты, защита от наследования будущего остатка, ноль/пустота, профиль/теги, повтор и конфликт batch_id, конкурирующие повторы и отмена транзакции при сбое перед сохранением результата. Ruff и pip check прошли. PostgreSQL запущен временно в analysis/work, без системной службы; рабочие данные заказчика не использовались. Docker-сборка всё ещё не проверена из-за отсутствия Docker.

Чтение реестра, карточка, пагинация истории и расчёты реализованы по ADR-0005. Проверены все виды динамики, переход года, календарная пара по умолчанию, полное обнуление и новая задержка, порядок строк одного пакета, теги, поиск, фильтры до пагинации, согласованность чтения при конкурентной записи и обезличенные ошибки. HTTP-чтение выключено по умолчанию. Локальное выполнение rollback и удаления реализовано по ADR-0006; документ clients-recovery-protocol.md определяет границы и обязанности координатора. До открытия записи на общем стенде согласовать авторизацию с Gateway. Глобальная координация Import/Operator Work, глобальное выполнение rollback/delete остаются отдельным этапом; локальные операции Clients готовы и по умолчанию выключены.

# Гипотеза: микросервис `ai-assistent` — ИИ-помощник по данным сервиса «Контур КЦР»

Дата: 2026-11-27
Статус: согласованная гипотеза. Сверка реализации от 28.11.2026: документация слита в dev (#106), шаг 2 завершён в ветке `feat/ai-assistent-mcp-server`; frontend начат отдельно в `feat/ai-assistent-frontend`. Полный MVP ещё не завершён. Реализация — отдельными небольшими PR по цепочке в §9 (подтверждение владельца от 28.11.2026).

## 1. Решения (согласованы с владельцем проекта)

| Вопрос | Решение |
|---|---|
| Стек | ai-assistent (TypeScript) **заменяет** запланированный Python Assistant Service; Node 26.12 |
| MCP-сервер | **Встроен** в ai-assistent (in-process, localhost Streamable HTTP) |
| LLM-провайдер | Отложен; модель задаётся конфигом env (провайдер-агностичность Vercel AI SDK) |
| Объём MVP | **Read-only** инструменты + заготовка подтверждений (`toolApproval`) |
| Новые фичи MCP | Подтверждено: Tasks, Skills, MCP Apps, Elicitation (спека 2026-07-28) |

## 2. Суть гипотезы

**Проблема.** Оператор перед звонком тратит время на сбор контекста из карточки (остатки, динамика, история звонков, обещания); администратор собирает списки на обзвон ручными фильтрами и не может сформулировать критерии словами.

**Гипотеза.** Если вынести ИИ-логику в отдельный TS-микросервис на Vercel AI SDK v7, который через MCP TS SDK v2 (спека 2026-07-28) читает факты из внутренних сервисов (Clients, Operator Work, Client History) через типизированные инструменты, то:

- оператор получает выжимку «контекст перед звонком» за секунды вместо минут;
- ответы строго основаны на фактах БД со ссылками на события (снижение риска галлюцинаций);
- администратор формирует приоритетные списки текстом, публикация списка остаётся за человеком.

**Критерий проверки:** слепое сравнение ответов ассистента с данными карточки + сравнение ИИ-списка с результатом эквивалентных фильтров `GET /api/v1/clients`.

## 3. Архитектура (один деплоймент-юнит)

```
Frontend (Next.js, useChat + формы elicitation + generative UI списков)
        │  /api/v1/assistant/*  (JWT → X-User-Id / X-User-Role)
        ▼
   Gateway / Identity (Go) — только новые маршруты
        ▼
┌──────────────────────────────────────────────┐      ┌────────────────┐
│ ai-assistent (TS, Node 26.12)                │      │ Облачный LLM   │
│  ┌────────────────────────────────────────┐  │      │ (провайдер     │
│  │ Агент: ToolLoopAgent (ai v7)           │◄─┼──────►  позже)       │
│  │  • toolApproval: 'user-approval'       │  │      └────────────────┘
│  │  • Output.object (схема списка)        │  │
│  │  • @ai-sdk/mcp createMCPClient (HTTP)  │  │
│  └──────────────┬─────────────────────────┘  │
│                 │ localhost MCP (Streamable   │
│                 ▼ HTTP, спека 2026-07-28)     │
│  ┌────────────────────────────────────────┐  │   X-User-Id / X-User-Role (ADR-0010)
│  │ MCP-сервер (встроенный):               │──┼──────► Clients Service
│  │  @modelcontextprotocol/server v2       │──┼──────► Operator Work Service
│  │  registerTool + zod v4, Skills,        │──┼──────► Client History Service
│  │  Elicitation (form)                    │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

- **Без собственной БД** — stateless: каждый запрос читает актуальные API; удалённые данные автоматически исчезают из контекста (требование spec.md §3.4).
- Протокол между агентом и MCP — настоящий MCP: elicitation, resources, skills идут по протоколу, а не приватными вызовами. Позже тот же MCP-сервер можно вынести или открыть наружу (Claude Code, Cursor) без переписывания агента.
- Межсервисное доверие — по ADR-0010: Gateway ставит `X-User-Id` / `X-User-Role`, внутренний контур изолирован сетью.

## 4. Функции и операции (read-only)

| Функция (ТЗ) | Операция | Роли | Инструменты MCP |
|---|---|---|---|
| Контекст перед звонком (5–7 пунктов) | `GET /api/v1/assistant/summary/{kcr_code}` | `ADMIN`, `OPERATOR` | `get_call_context`: остатки по исходным кварталам, динамика к прошлому срезу, номер звонка, последний звонок, обещания и статус, этап/wait_until |
| Вопросы по состоянию клиента и динамика за выбранный период | `POST /api/v1/assistant/chat/{kcr_code}` — поток UI message stream | `ADMIN`, `OPERATOR` | `get_client_card`, `get_snapshot_history`, `get_history_events`; ответ со ссылками `EventReference` |
| Приоритетный список на обзвон словами | `POST /api/v1/assistant/filter-query` | `ADMIN` | `query_clients`: текст → фильтры `GET /api/v1/clients` (dynamics, duration, tags, числовые диапазоны, quarter); ответ `{items: [{kcr_code, reason}], total, criteria, not_applied}` |

- Чат закреплён за клиентом из маршрута: `{kcr_code}` в пути, видимость оператора проверяет Gateway как для карточки (ADR-0014, ADR-0018). До этого `chat` был доступен только `ADMIN` — смена ролей отмечена в PR #106 как решение на проверку.
- Публикация списка — только руками администратора через существующий `PUT /api/v1/pool/publication`.
- Источники данных инструментов (внутренние API): Clients — `GET /clients`, `GET /clients/{kcr_code}`, `GET /clients/{kcr_code}/snapshots/history`; Operator Work — `GET /clients/{kcr_code}/work-state`, `/assignment`, `/cycles`, `POST /clients/current-assignees`; Client History — `GET /clients/{kcr_code}/events`.

## 5. Применение новых фич MCP

| Фича | Применение | Этап |
|---|---|---|
| **Запрос на ввод (Elicitation / input required)** | Уточнение недостающих данных: период динамики в чате, порог и объём выборки при отборе. В спеке 2026-07-28 инструмент возвращает запрос на ввод вместо результата, агент останавливается, пользователь отвечает в интерфейсе, вызов повторяется с ответом. Состояние переносит диалог, сервер ничего не удерживает | MVP |
| **Skills over MCP** | `SKILL.md`-файлы в репо сервиса (терминологический бан; правила кварталов и переноса остатков; шаблон выжимки) — встроенный сервер отдаёт их через `skills/list` и `resources/read` | MVP |
| **Tasks** (ext-tasks) | Генерация списка по всей базе как долгая операция: task handle, polling, возобновление после реконнекта | Фаза 2 |
| **MCP Apps** | Интерактивный график динамики в чате; в собственном UI проще generative-UI tool parts | Фаза 2, опционально |

## 6. Честность и безопасность

- Только факты из инструментов; нехватка данных → прямой отказ, без выдумок (ТЗ №4).
- Облачный провайдер (уточнение от 05.11.2026): в промпт — только данные конкретного клиента/агрегаты, без полных выгрузок; публикация выгрузок в открытом доступе запрещена.
- Терминологический бан («долг», «задолженность», «должник») — в Skill и системном промпте; проверяется приёмочными тестами.
- Изменяющих действий в MVP нет; каркас `toolApproval` — под будущие сценарии (ТЗ: ИИ не меняет этапы/статусы/обзвон без подтверждения сотрудника).

## 7. Приёмка гипотезы

1. Ответы ассистента совпадают с данными карточки/журнала (слепая сверка выборки).
2. ИИ-список совпадает с результатом эквивалентных фильтров `GET /api/v1/clients`.
3. Ссылки на события в ответах существуют в Client History.
4. Отказ при отсутствии данных, а не выдумка.
5. Бан терминов соблюдён.

## 8. Риски

1. Стек против текущего spec.md/AGENTS.md (Assistant = Python) — закрывается ADR-0022 и правками spec.md; существующие ADR не редактируются.
2. CI `assistant-service-pr-checks.yml` заточен под Python/Poetry — под TS обновляет владелец CI (свои CI не пишем).
3. Второй TS-стек в мире Python-сервисов — инфраструктура Node 26.12 уже есть (mise, фронтенд).
4. Галлюцинации в критериях отбора — митигируется детерминированной частью (критерии → фильтры API, а не LLM-перебор).
5. Скорость/стоимость облачного провайдера — выбор модели отложен.

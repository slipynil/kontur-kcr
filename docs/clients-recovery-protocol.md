# Протокол восстановления и удаления Clients

Основание — ADR-0006. Здесь разделены работающая локальная часть Clients и обязанности будущего координатора Import. Ответ `local_only=true` не является подтверждением глобальной операции.

## Команда

Для отката и обоих видов удаления тело содержит `operation_id` и `requested_by` (UUID). ID сохраняется координатором до первого вызова и повторяется после любого таймаута. Новый ID означает новую команду. Объект передаётся путём:

- `POST /internal/v1/import/{batch_id}/rollback`;
- `DELETE /internal/v1/clients/{kcr_code}`;
- `DELETE /internal/v1/clients/{kcr_code}/snapshots/{quarter}`.

DELETE с JSON-телом — внутренний контракт; Gateway должен сохранить тело или преобразовать публичный запрос в эту команду. `requested_by` фиксирует автора, но не подтверждает право вызова. Доверенная идентичность сервиса и пользователя должна проверяться отдельным согласованным механизмом.

## Локальное выполнение

Clients сериализует apply/rollback/delete общим PostgreSQL advisory lock. В транзакции проверяются повтор operation_id, существование пакета и его локальный порядок. Затем меняются данные, сохраняются undo и ответ команды. Успешный ответ отправляется после commit. Ошибка/таймаут БД оставляет операцию незавершённой; повторить нужно тот же ID и payload.

Одинаковый ID с другим действием, объектом или автором возвращает `409 OPERATION_PAYLOAD_CONFLICT`. Отсутствующий клиент/квартал при удалении даёт 200 и нулевые счётчики. Неизвестный пакет — `404 IMPORT_NOT_FOUND`. Более ранний активный локальный пакет — `409 IMPORT_NOT_LATEST`. Повтор apply отменённого batch_id — `409 IMPORT_ALREADY_ROLLED_BACK`; для новой загрузки нужен новый пакет.

Повтор уже выполненного rollback с новым operation_id возвращает результат с `already_rolled_back=true` и не повторяет изменения. Поэтому удаление, выполненное уже после завершённого отката, повторным rollback не отменяется.

## Восстановление после ручного удаления

Пакет обновил Q1 и Q2. Администратор удалил Q1. Откат пакета возвращает Q1 и Q2 в состояние до пакета, включая наблюдения истории Q1. Именно это выбрал пользователь; предварительное предложение оставлять Q1 удалённым отменено.

Восстановление ограничено клиентами, затронутыми пакетом. Удалённый другой клиент не появляется. Удаление, выполненное до применения откатываемого пакета, является частью его исходного состояния и не отменяется. Наблюдения откатываемого и уже отменённых пакетов не восстанавливаются из копий удаления.

Рабочие таблицы и Registry API перестают содержать удалённую историю сразу после локального удаления. Для обратимости история сохраняется в `clients_deleted_history`, а профиль/теги/срезы до импорта — в `clients_import_undo`. Это закрытые восстановительные копии, они не выдаются HTTP-чтением. Технический журнал хранит только метаданные и результат; срок хранения/необратимое уничтожение undo отдельно не определены.

## Порядок пакетов до миграции

Новые apply получают монотонный apply_order. Для старых операций миграция оставляет NULL: время создания транзакции не доказывает порядок применения конкурентных запросов. Один оставшийся старый пакет допускается к локальному откату; несколько старых активных пакетов возвращают `409 IMPORT_ORDER_UNKNOWN`. До включения общего стенда координатор должен установить достоверный порядок по своему журналу; открытого API угадывания или изменения порядка в Clients нет.

## Обязанности координатора, ещё не реализованные

1. Принять действие от авторизованного администратора, сохранить команду и объект в своей БД. Сериализовать глобальное применение и откаты, чтобы новый пакет не применился между проверкой глобального последнего пакета и завершением восстановления.
2. Для rollback проверить глобальный последний применённый неотменённый пакет, включая пакеты без принятых клиентских строк. Локальная проверка Clients этого не заменяет.
3. Вызвать Clients с устойчивым operation_id. При потере ответа повторить ту же команду; не создавать новый ID для каждого HTTP-повтора. При 409 разрешить конфликт, при 503 повторить по принятой политике доставки. Точные интервалы/лимиты доставки ещё согласуются.
4. Согласованно очистить или восстановить Operator Work и кэши других сервисов. Для восстановления операторской истории соседнему сервису понадобится собственный undo. При квартальном удалении сохранить другие кварталы и общие звонки/договорённости.
5. Отметить глобальное завершение и вернуть публичный успех только после всех участников. Частично выполненная операция остаётся в журнале координатора для продолжения; отдельные локальные ACID-транзакции не образуют общей транзакции.

До реализации этих обязанностей и авторизации `CLIENTS_ENABLE_DATA_RECOVERY` по умолчанию false. Включение предназначено только для изолированной разработки. Clients не вызывает Operator Work и не пишет в чужие БД.

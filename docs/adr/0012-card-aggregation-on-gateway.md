# 0012. Агрегация публичной карточки на Gateway

## Status

Accepted — решение пользователя от 17.11.2026 (вариант «агрегация на Gateway»).

## Context

Публичная карточка `GET /api/v1/clients/{kcr_code}` описана как агрегат: профиль и срезы принадлежат Clients, а `work_quarter`, `assignment_id`, `current_stage`, `assignment`, `wait_until` — Operator Work (spec.md §3.6). Фактически Gateway проксировал запрос только в Clients, поэтому рабочие поля в ответе отсутствовали: фронтенд не знал квартал цикла и ответственного, кнопка «Взять в работу» оставалась отключенной у опубликованного клиента (docs/e2e-findings.md §4).

## Decision

Gateway собирает карточку сам, не меняя публичный API и не трогая фронтенд:

1. Параллельно читаются два внутренних источника: карточка Clients `GET /internal/v1/clients/{kcr_code}` (с параметрами запроса как есть) и рабочее состояние Operator Work `GET /internal/v1/clients/{kcr_code}/work-state` — новый внутренний эндпоинт без обязательного квартала: без `work_quarter` возвращает состояние текущего цикла, с ним — указанного (исторический даёт 409).
2. Gateway мержит рабочие поля в JSON Clients и разрешает `operator_name` по Identity DB (логин пользователя; удалённый пользователь даёт пустое имя).
3. Ошибки:
   - Clients — источник карточки: его 4xx/5xx уходят наружу как есть (как при проксировании), сетевая ошибка — 503.
   - Operator Work: 404 («нет действующего цикла / клиент не опубликован») — карточка отдаётся с пустыми (null) рабочими полями; 409 исторического цикла проходит наружу; любая другая ошибка, включая недоступность сервиса, срывает ответ целиком со статусом 502 `BAD_GATEWAY`. Деградация «карточка без рабочих полей» отклонена решением пользователя.

## Consequences

Кнопка «Взять в работу» в карточке активна у опубликованного свободного клиента, «Этап» и «Ответственный» заполняются из Operator Work. Публичный контракт дополняется статусами 409/502 и nullable `current_stage` (public-api.yaml); внутренний контракт Operator Work дополняется `readClientWorkState`. Список `GET /api/v1/clients` продолжает идти в Clients напрямую; батч-агрегация списка (колонки «Этап»/«Ответственный») — отдельная задача. Лента событий по-прежнему показывает сырые `author_id` — тот же класс задач об именах.

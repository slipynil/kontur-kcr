# 0001. Разделить систему на микросервисы по предметным областям

## Status

Proposed

## Context

Текущая система построена как распределённый монолит. Центральное ядро содержит бизнес-логику, и через него проходят все запросы к остальным частям системы. Ядро стало узким местом: оно замедляет выполнение запросов, а любое изменение в нём затрагивает всю систему.

Над системой работает команда из 5 человек с разными стеками (Go, Python). Нужно распределить зоны ответственности так, чтобы каждый участник мог развивать свою часть независимо и на своём стеке.

Системой пользуются операторы и администраторы.

**Оператор:**

1. Войти в систему
2. Найти клиента по коду КЦР или ИНН
3. Работать с общей таблицей клиентов
4. Открыть карточку клиента
5. Открыть список «Сегодня нужно»
6. Взять клиента в работу
7. Освободить клиента
8. Зафиксировать звонок

**Администратор:**

1. Войти в систему
2. Загрузить в реестр клиентов и срезы из Excel
3. Увидеть динамику после загрузки
4. Найти клиента по коду КЦР или ИНН
5. Работать с общей таблицей клиентов
6. Открыть карточку клиента
7. Сформировать список на обзвон
8. Снять клиента с оператора
9. Управлять пользователями и ролями

Также в системе планируется AI-ассистент, который помогает оператору и выполняет операторские сценарии через чат.

**Ограничения от заказчика:**

- никаких интеграций с системами Контура;
- обмен данными через Excel;
- только тестовые данные;
- архитектура должна позволить позже заменить импорт из Excel на API.

## Considered Options

1. **Доработать текущее ядро.** Не решает главную проблему: бизнес-логика остаётся в одной точке, через которую идут все запросы.
2. **Модульный монолит.** Позволяет разделить код на модули, но требует единого языка и единого развёртывания. При разных стеках в команде (Go и Python) это невозможно.
3. **Микросервисы с границами по предметным областям.**

## Decision

Выбран вариант 3. Система делится на пять сервисов, каждый владеет своими данными и своей зоной ответственности.

### Gateway / Identity

**Отвечает за:** аутентификацию и авторизацию пользователей, управление пользователями и ролями, маршрутизацию запросов от фронтенда к сервисам.

**Почему отдельный сервис:** Gateway — единая точка входа, поэтому он намеренно тонкий: только проверка токена и маршрутизация, без бизнес-логики. Этим он принципиально отличается от старого ядра. Через него проходит вся нагрузка, поэтому он должен быть быстрым — отсюда выбор Go.

**Стек:** Go

### Import Service

**Отвечает за:** загрузку реестра клиентов и срезов из Excel.

**Почему отдельный сервис:** источник данных изолирован в отдельном сервисе. При замене Excel на API меняется только Import, а Clients и остальные сервисы не затрагиваются. Кроме того, обработка больших файлов идёт асинхронно и не нагружает сервисы, с которыми работают операторы.

**Стек:** Python

### Clients Service

**Отвечает за:** реестр клиентов и историю срезов: поиск по КЦР и ИНН, общая таблица, карточка клиента, динамика после загрузки.

**Почему отдельный сервис:** реестр — это справочник. Он меняется в основном при импорте, и его главная задача — хранить и отдавать данные о клиентах. Процесс работы операторов с клиентами устроен иначе и меняется постоянно в течение дня. Разделение не даёт правилам обзвона смешиваться с хранением реестра.

**Стек:** Python

### Operator Work Service

**Отвечает за:** процесс обзвона: формирование списков на обзвон, список «Сегодня нужно», взятие клиента в работу, освобождение, снятие клиента с оператора, фиксацию звонков.

**Почему отдельный сервис:** здесь живёт бизнес-логика процесса обзвона: кто из операторов какого клиента ведёт, какие звонки сделаны, кому нужно позвонить сегодня. Эти правила не относятся к реестру клиентов и развиваются отдельно. Поскольку AI-ассистент помогает именно в операторских сценариях, его действия выполняются через внешний инструмент MCP Server, который вызывает только этот сервис.

**Стек:** Python

### Assistant Service

**Отвечает за:** взаимодействие пользователей с AI-ассистентом через чат.

**Почему отдельный сервис:** мы планируем использовать разные модели ИИ. Изоляция ассистента в отдельном сервисе позволяет менять модель и логику ассистента, не затрагивая остальную систему.

**MCP Server — внешний инструмент, вне границы системы** (как LLM). Assistant Service вызывает его инструменты, а MCP Server выполняет операторские действия через Operator Work Service. Замена или обновление MCP Server не затрагивает систему.

**Стек:** Python

### Слои контейнеров

Внутри границы системы контейнеры организованы по слоям сверху вниз:

1. **Presentation Layer** — Web App (SPA) и nginx: доступ пользователей, терминирование HTTPS.
2. **Business Layer** — сервисы с бизнес-логикой: Gateway / Identity, Import API + Import Worker, Clients, Operator Work, Assistant.
3. **Persistence Layer** — RabbitMQ: буферизация и передача данных (очередь задач импорта).
4. **Database Layer** — PostgreSQL: отдельная БД у каждого сервиса, который хранит данные.

Схема архитектуры: [C4 L2: диаграмма контейнеров](../c4-l2-container-diagram.html)

## Consequences

**Плюсы:**

1. Каждый участник команды отвечает за свой сервис и работает на своём стеке.
2. Сервисы развёртываются независимо: изменение в одном не требует пересборки остальных.
3. Сбой Import или Assistant не влияет на основную работу операторов.
4. Замена Excel на API затрагивает только Import Service.
5. Сервисы можно масштабировать по отдельности, например Gateway или Clients при росте нагрузки.

**Минусы:**

1. Operator Work получает данные клиентов через сетевой вызов в Clients — это медленнее локального вызова и добавляет точку отказа.
2. Нужно поддерживать согласованность данных: клиент может быть в работе у оператора, когда новый импорт изменил или удалил его в реестре.
3. Gateway — единая точка отказа: если он недоступен, недоступна вся система.
4. Два языка (Go и Python) — два набора инструментов, линтеров, Dockerfile и CI-пайплайнов.
5. Больше инфраструктуры: несколько сервисов, несколько БД, брокер сообщений. Развёртывание и отладка сложнее, на старте больше инфраструктурной работы.
6. Нужна трассировка запросов между сервисами, иначе ошибки трудно искать.

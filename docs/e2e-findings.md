# Сбои E2E на локальном стенде

Стенд собран из коммита `fceba39`. Полный прогон дал 40 успешных, 6 упавших и 2 пропущенных проверки. Пропущенные проверки требуют исходных выгрузок Дубны. Номера строк серверного и клиентского кода сверены с коммитом стенда. Ссылки на тесты указывают на текущую рабочую копию.

## 1. Импорт остаётся в PROCESSING

**Где.** Import Worker, [consumer.py:130](../services/import-worker/import_worker/consumer.py#L130). В ветке с принятыми строками воркер записывает `clients_applied_at` и очищает `apply_payload`. На стенде после этого пакет не переходит в конечный статус.

| Сценарий | Что произошло |
|---|---|
| [Администратор загружает реестр](../tests/admin-data.e2e.ts#L53) | Браузер открыл отчёт. В базе Import одна принятая строка, ошибок нет. Через 30 секунд статус оставался `PROCESSING`. |
| [Администратор загружает срез со смешанными строками](../tests/admin-data.e2e.ts#L74) | В базе Import одна принятая строка и три ошибки. Ожидание `COMPLETED` истекло. |
| [Администратор откатывает последний пакет](../tests/admin-data.e2e.ts#L134) | Первый подготовительный импорт остался в `PROCESSING`. Тест остановился до отправки запроса на откат. Ответ на откат раннего пакета и очистка работы после отката последнего остаются непроверенными. |

**Что исправить.** Довести координацию импорта до подтверждения всех обязательных шагов. Для среза это включает обновление циклов Operator Work. После подтверждений выставить `COMPLETED` и `completed_at`. Сохранённый результат Clients должен позволять продолжить с неподтверждённого шага. После исправления проверить отказ `409 IMPORT_NOT_LATEST` для раннего пакета и очистку работы по данным, удалённым при откате последнего. [Контракт координации](api/import-operator-work-contract.md)

## 2. Годовой лист попадает в обработку среза

**Где.** Import Worker, [parser.py:76](../services/import-worker/import_worker/parser.py#L76) и [parser.py:90](../services/import-worker/import_worker/parser.py#L90). Проверка названия распознаёт, например, `2026 год`, но пропускает формат `весь 2026 год`.

**Сценарий.** В [тесте смешанного среза](../tests/admin-data.e2e.ts#L74) годовой лист содержал строку с КЦР, который уже был в квартальном листе. В базе причина отклонения этой строки — «Дубликат строки в пакете (client.kcr_code)». Это подтверждает, что строка годового листа дошла до обработки. Тест отдельно ждёт пропуска листа с указанием причины, но сейчас останавливается раньше на `PROCESSING`.

**Что исправить.** Распознавать формат «весь ГГГГ год» и пропускать лист до разбора строк. В тесте проверить причину пропуска и то, что годовой лист с отдельным КЦР не создаёт срез. Для ошибки неизвестного КЦР проверять основную причину отдельно от суффикса с именем поля, который добавляет [consumer.py:123](../services/import-worker/import_worker/consumer.py#L123).

## 3. Gateway не принимает запросы на удаление

**Где.** Gateway, [server.go:77](../services/gateway/internal/server/server.go#L77) и [server.go:88](../services/gateway/internal/server/server.go#L88). В группе администратора отсутствуют оба маршрута `DELETE`. Для карточки клиента зарегистрирован `GET`.

| Сценарий | Фактический ответ | Что проверить после исправления |
|---|---|---|
| Администратор подтверждает «Удалить квартал» | `DELETE /api/v1/clients/{kcr_code}/snapshots/{quarter}` → `404` | Выбранный срез и относящиеся только к нему события исчезают. Остальные кварталы, общий комментарий и незатронутый цикл сохраняются. |
| Администратор подтверждает «Удалить клиента» | `DELETE /api/v1/clients/{kcr_code}` → `405` | Карточка недоступна, связанные циклы, назначения и события очищены. |

**Что исправить.** Подключить оба маршрута с правами администратора и передать операции координатору. Публичный успех возвращается после подтверждения очистки во всех затронутых сервисах. Внутренние обработчики удаления уже есть в [Clients Service](../services/clients/src/clients_service/recovery_api.py#L17). Ожидаемое публичное поведение зафиксировано в контрактах [удаления клиента](api/public-api.yaml#L534) и [удаления квартала](api/public-api.yaml#L854). [Сценарии E2E](../tests/admin-data.e2e.ts#L185)

## 4. Кнопка «Взять в работу» отключена у опубликованного клиента

**Где.** Frontend, [clients.tsx:28](../frontend/components/clients.tsx#L28), [clients.tsx:35](../frontend/components/clients.tsx#L35) и [clients.tsx:48](../frontend/components/clients.tsx#L48). Карточка берёт `work_quarter` из ответа Clients и отключает кнопку при его отсутствии. Gateway отправляет запрос карточки в Clients Service. Рабочий цикл живёт в Operator Work, а отдельного запроса за ним у фронтенда нет. [Маршрут карточки](../services/gateway/internal/server/server.go#L88) · [Внутреннее чтение назначения](../services/operator-work/operator_work/api.py#L180)

**Сценарий.** Фикстура опубликовала свободного клиента. Оператор открыл карточку, кнопка осталась отключённой. Тест остановился до отправки `POST /take`. Взятие через API и гонка двух операторов прошли в отдельных проверках. [Браузерный сценарий](../tests/operator.e2e.ts#L56)

**Что исправить.** Подключить отдельное чтение рабочего состояния через Gateway к Operator Work. Фронтенд запрашивает профиль и рабочее состояние отдельно и использует квартал обзвона, назначение, этап и дату ожидания для выбора доступного действия. Проверка после исправления должна пройти от открытой карточки до появления нового ответственного, а для клиента с действующим `WAIT_DEADLINE` сохранить блокировку перезакрепления.
